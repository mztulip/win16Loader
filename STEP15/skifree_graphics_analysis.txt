SkiFree GDI Call Analysis — STEP15
====================================
(captured via serial trace, 600 calls)

=== GDI FUNCTIONS USED BY SKIFREE ===

1. GetDeviceCaps(hdc, nIndex)
   - Called during WM_CREATE to query screen dimensions.
   - Indices used: HORZRES(8), VERTRES(10), BITSPIXEL(12), RASTERCAPS(38).
   - SKI.EXE uses min(HORZRES, VERTRES) as the game window size.
   - We return HORZRES=VERTRES=640 so window = 640x640.

2. CreateCompatibleDC(hdc)
   - Called 5 times during WM_CREATE: creates DC2..DC6.
   - Win16: allocates a "memory DC" compatible with the screen.
   - Our impl: allocates a 640x480x4 BGRA pixel buffer from XMS (19 GDT windows each).
   - All pixels start as alpha=0 (transparent).

3. CreateCompatibleBitmap(hdc, w, h) / CreateBitmap(...)
   - Called to create bitmap objects associated with atlas DCs.
   - Results: HBM 0x57 (small sprite atlas bitmap), 0x59 (large sprite atlas),
     0x58 / 0x5A (mask atlases — CreateBitmap, inverted).
   - Our impl: returns a fake handle (sequential number >= 87).

4. SelectObject(hdc, hObject)
   - Binds a bitmap to a DC: g_dc_bitmap[hdc] = hObject.
   - During atlas init: SelectObject(DC6, sprite_N) sets DC6's "source bitmap" to sprite N.
   - DC6 is then used as source in BitBlt so that src_hbm = sprite_N triggers Case 1.
   - Returns previous HBITMAP.

5. BitBlt(hdcDst, xDst, yDst, w, h, hdcSrc, xSrc, ySrc, dwRop)
   - Core sprite rendering function. Multiple cases depending on DC types and ROP.
   - See "RENDERING PIPELINE" section below.

6. TextOut(hdc, x, y, str, len)
   - Renders text using the 8x16 ROM font.
   - Called for HUD text (Time/Dist/Speed/Style) and title screen text.

7. GetTextExtent(hdc, str, len) / GetTextMetrics(hdc, lptm)
   - Used to measure text for layout (button sizes, status bar).

8. GetStockObject(nObject)
   - Returns stock objects (brushes, pens): encoded as 0x8000|nObject.
   - Used in SelectObject calls for window/button drawing.

9. PatBlt(hdc, x, y, w, h, dwRop)
   - Fills rectangle with current brush (WHITENESS/BLACKNESS).
   - NOTE: Not seen in the 600-call trace — may be used for background fill
     or in messages not reached within trace limit.

10. DeleteDC / DeleteObject
    - Cleanup stubs. No-op in our implementation.

11. GetObject(hObject, cbBuffer, lpObject)
    - Fills BITMAP struct for a given HBITMAP.
    - Used by SKI.EXE to get sprite dimensions (bmWidth, bmHeight).


=== DC MAP ===

DC 1  = screen DC (maps to LFB at 0xFD000000, pitch=1920, 3 bytes/px BGR)
DC 2  = small sprite atlas  (sprites w<=32px)  buf_sel=0x0130  HBM=0x57
DC 3  = small mask atlas    (NOTSRCCOPY)        buf_sel=0x01C8  HBM=0x58
DC 4  = large sprite atlas  (sprites w>32px)   buf_sel=0x0260  HBM=0x59
DC 5  = large mask atlas    (NOTSRCCOPY)        buf_sel=0x02F8  HBM=0x5A
DC 6  = compositing memDC   (per-frame)         buf_sel=0x0390  HBM=0x5B

Selector spacing: 19 descriptors * 8 bytes = +0x98 per DC.
DC buffer layout: 640x480 * 4 bytes = 1,228,800 bytes = 19 * 64KB GDT windows.
Pixel format: BGRA — [B][G][R][A] where A=0=transparent, A=1=opaque.


=== RENDERING PIPELINE (BitBlt cases) ===

Case 1: sprite(1..86) → memDC, SRCCOPY
  Condition: src_hbm in 1..86, hdcDst in 2..15, ROP=CC (SRCCOPY)
  Action: decode 4bpp sprite pixels from SEL_BITMAPS, write to dst buffer.
          Transparent pixels (palette idx 15 = white) skipped (alpha stays 0).
  Used for: atlas building during WM_CREATE. Each sprite blitted at yDst=row_offset.

Case 2B: memDC → memDC, SRCCOPY
  Condition: hdcSrc in 2..15, hdcDst in 2..15, ROP=CC
  Action: copy src buffer pixels (alpha=1 only) to dst buffer.
  Used for: DC4 (atlas row) → DC6 (compositing DC) each frame.
  Important: only alpha=1 pixels copied, so transparent regions stay clear.

Case A: screen(1) → memDC, SRCCOPY
  Condition: hdcSrc=1, hdcDst in 2..15, ROP=CC
  Action: copy screen pixels into memDC buffer (background capture).
  NOT observed in the 600-call trace for SKI.EXE.

Case B: ANY → memDC, SRCAND(88) or SRCPAINT(EE)
  Condition: hdcDst in 2..15, ROP=88 or EE
  Sub-case Bsprite: src is real sprite (1..86)
    SRCPAINT(EE): write sprite pixels to buffer
    SRCAND(88): write black where sprite opaque (mask operation)
  Sub-case Bmemdc: src is memDC
    SRCPAINT(EE): copy alpha=1 pixels from src buffer
    SRCAND(88): no-op (would cause solid rectangles — SRCAND on memDC is skipped)
  NOT observed in game loop trace for SKI.EXE — only during potential init paths.

Case C: memDC → screen(1), SRCCOPY
  Condition: hdcDst=1, hdcSrc in 2..15, ROP=CC
  Action: blit alpha=1 pixels from src buffer to LFB. Auto-clears alpha after read.
          Transparent (alpha=0) pixels don't overwrite background.
  Used for: DC6 → screen each frame.

Case 4: sprite(1..86) → screen, SRCCOPY
  Condition: src_hbm in 1..86, hdcDst=1, ROP=CC
  Action: direct 4bpp→LFB blit via blit_sprite_hbm (no intermediate buffer).
  NOT observed in the 600-call trace for SKI.EXE.


=== CALL SEQUENCE: WM_CREATE (atlas init) ===

1. GetDeviceCaps(HORZRES=8), GetDeviceCaps(VERTRES=10) [garbled in trace - DS!=SS bug]
2. RegisterClass(proc=0030:4C9A)  [WndProc]
3. RegisterClass(proc=0030:513C)  [status bar WndProc]
4. CreateWindow(main) -> WM_CREATE:
   a. CreateCompatibleDC x5 -> DC2..DC6 (640x480 BGRA buffers)
   b. CreateCompatibleBitmap(DC2,w,h) -> HBM 0x57
   c. SelectObject(DC2, 0x57)
   d. CreateBitmap(1,h,1,1,0) -> HBM 0x58
   e. SelectObject(DC3, 0x58)
   f. CreateCompatibleBitmap(DC4,w,h) -> HBM 0x59
   g. SelectObject(DC4, 0x59)
   h. CreateBitmap(1,h,1,1,0) -> HBM 0x5A
   i. SelectObject(DC5, 0x5A)
   j. FOR sprite N = 1..86:
      - SelectObject(DC6, N)
      - BitBlt(DC2 or DC4, 0, yOff, w, h, DC6, 0, 0, SRCCOPY=CC) [Case 1]
      - BitBlt(DC3 or DC5, 0, yOff, w, h, DC6, 0, 0, NOTSRCCOPY=33) [unhandled, no-op]
      - SelectObject(DC6, 1) [reset DC6]
      DC2/DC3 for w<=32px sprites; DC4/DC5 for w>32px sprites.
      yOff accumulates: each sprite stacked vertically in atlas.
   k. CreateCompatibleBitmap -> HBM 0x5B
   l. SelectObject(DC6, 0x5B)
5. CreateWindow(status_child) -> WM_CREATE:
   a. SelectObject(HWND-DC 0x4002, GetStockObject(SYSTEM_FONT=0xA))

=== CALL SEQUENCE: Game loop (WM_USER+2 = 0x1002) ===

Per frame (18 Hz, one IRQ0 tick):

1. BitBlt(DC6, 0, 0, w, h, DC4, 0, ySrc, SRCCOPY)
   [Case 2B: copy sprite row ySrc from large atlas DC4 into DC6 at (0,0)]
   ySrc changes each frame to select the current animation frame.

2. BitBlt(screen=1, xDst, yDst, w, h, DC6, 0, 0, SRCCOPY)
   [Case C: blit DC6 to screen at sprite position. Auto-clears DC6 after blit.]

NOTE: Only large sprites (DC4) visible in the 600-call game loop trace.
Small sprites (DC2) and SRCAND/SRCPAINT may appear later or for specific objects.
No background clear (PatBlt) observed — background is left from previous frame
except where sprites are blitted. SKI.EXE relies on the snow-white background
being preserved (no background rendering after initial setup).


=== KEY BUGS FOUND AND FIXED ===

1. decode_4bpp_pixel: DS!=SS output parameter bug
   PROBLEM: Function had output params (unsigned char *r_out etc.) — near pointers.
   In Win16 DLL context DS=DGROUP != SS=app_stack. Writing *r_out via near ptr uses DS.
   Stack locals passed as &rv1 are on SS. Writes go to wrong DS address -> rv1/tr1 garbage.
   tr1 (transparency flag) stays uninitialized -> all pixels treated as opaque -> SOLID RECTANGLES.

   FIX: Changed return type to unsigned long (DX:AX register return, no memory writes):
   - Return 0x01000000 for transparent
   - Return (R<<16)|(G<<8)|B for opaque
   Callers check (pix & 0x01000000) for transparency, extract R/G/B from low 24 bits.

2. serial_putdec: stack buffer DS!=SS bug
   PROBLEM: char buf[8] on stack; serial_puts(buf+i) reads via DS -> garbage output.
   FIX: static char buf[8] (in DGROUP, read via DS correctly).

3. SRCAND from memDC source: solid rectangle bug (STEP15g)
   PROBLEM: BitBlt(DC6, ..., DC3_mask, ..., SRCAND) wrote black+alpha=1 where mask=opaque,
   including sprite-transparent interior. Case C blitted these black pixels to screen.
   FIX: SRCAND from memDC source is a no-op (only SRCPAINT handled for memDC→memDC).

=== MECHANIZM ZEGAROWY (jak gra odmierza czas) ===

Łańcuch:
  Sprzęt PIT (8253) -> IRQ0 co ~55ms (18.2 Hz, domyślny divisor=65536)
    -> irq0_handler (IDT[0x20], pm_call.asm):
         add word [KCB+28], 55   ; low word licznika ms
         adc word [KCB+30], 0    ; carry do high word
    -> GetTickCount() (user.c):
         return *(unsigned long*)(KCB+28)  ; ms od startu

Jak gra odmierza 20 sekund do startu gondoli:
  start_tick = GetTickCount();             // zapisz czas startu
  // ... każda klatka ...
  if (GetTickCount() - start_tick > 20000) // 20000 ms = ~363 ticki IRQ0
      gondola_active = 1;

Pętla gry (PeekMessage w user.c) czeka na zmianę licznika:
  t0 = *tick_p;
  while (*tick_p == t0) {}   // blokuj do następnego IRQ0 (~55ms)
  -> jedna klatka = jeden tick IRQ0 = ~55ms -> ~18 klatek/s

SKI.EXE NIE używa SetTimer/WM_TIMER (brak SetTimer w importach USER).
Cały timing oparty wyłącznie na GetTickCount().

TimerProcMain (eksport ord=1 @ CS:0x3597): callback wywoływany ręcznie
z pętli gry lub wcześniejszy mechanizm — nie przez WM_TIMER.

Diagnoza ruchu gondoli:
  Zegar działa poprawnie (IRQ0 co 55ms, GetTickCount OK).
  Problem nie leży w odmierzaniu czasu — gondola nie rusza się
  z powodu braku ruchu współrzędnych x/y na ekranie (błąd renderowania).

=== CALL TRACK: NPC NARCIARZ (sprity #37-44) ===

Drugi narciarz przelatuje przez ekran losowo; używa 8 wariantów kierunkowych.

--- System encji (entity linked list) ---

SKI.EXE zarządza listą encji (obiektów ruchomych) zaczepioną w [0xb7c].
Inicjalizacja w render_or_state (CS:0x3CEB), pool 0x1A00 = 6656 bajtów.

Struktura encji (~52 bajty):
  +0x00  ptr do następnej encji (linked list)
  +0x06  pod-licznik / stan pomocniczy
  +0x08  ID sprite'a bieżącej klatki (aktualizowany przez sprite selection)
  +0x0A  licznik wieku / tick
  +0x0C  TYP encji (0=przeszkody, 1=?, 2=?, 3=NPC narciarz, 9=yeti)
  +0x0E  stan animacji (0x1F..0x27 dla NPC)
  +0x10  delta-X na klatkę (prędkość X w jednostkach świata)
  +0x12  delta-Y na klatkę (prędkość Y)
  +0x14  licznik czasu trwania
  +0x16  baza X (pozycja startowa w układzie świata)
  +0x18  baza Y
  +0x20  bieżąca X w świecie
  +0x22  bieżąca Y w świecie
  +0x24  flaga widoczności / warunek aktywności
  +0x26  prędkość X (aktualizowana przez fizykę)
  +0x28  prędkość Y
  +0x2C  bajt flag

--- Typy encji ---

Typ 3 = NPC narciarz (entity_type3 @ CS:0x2594)
Typ 9 = yeti          (entity_type9 @ CS:0x251E, stany 0x38-0x3C)
Typ 0 = przeszkody    (drzewa, muldy itp.)

--- Maszyna stanów NPC (CS:0x2594) ---

Stan 0x1F (31) – uśpiony:
  rand(10): wynik==0 (1/10 szans/klatkę) → stan→32  (aktywacja)
           wynik!=0 (9/10)               → pozostań w stanie 31

Stan 0x20 (32) – aktywny / "na starcie":
  rand(10): wynik==0 (1/10)  → stan→31  (deaktywacja)
           wynik!=0 (9/10)  → pozostań w stanie 32

Stan 0x21 (33) – warunek startu:
  if [encja+0x24] != 0: pozostań → normalne renderowanie
  if [encja+0x24] == 0: stan→31  (warunek nie spełniony → znikaj)

Stany 0x22-0x27 (34-39) – cykl animacji (6 klatek):
  co klatkę: stan++; jeśli stan==39 → stan=32
  Pętla: 34→35→36→37→38→39→32→(32 z losowością)

Przy ~25 klatkach/s i prawdopodobieństwie 1/10 na klatkę:
  Oczekiwany czas do aktywacji z stanu 31 ≈ 10×0.04s = 0.4s.
  Aktywny przez kilka sekund (stany 34-39 wracają do 32, skąd 9/10 zostaje).
  Opuszcza ekran gdy [encja+0x24] stanie się 0 (wyjście poza granicę widoku).

--- Wybór sprite'a (CS:0x2D41) ---

Sprite wybrany na podstawie prędkości bieżącej klatki:
  [encja+0x0C] >= 0x5C00  (duże +X): sprite 0x27 = 39  (jedzie w prawo szybko)
  [encja+0x0C] <= -0x400  (duże -X): sprite 0x29 = 41  (jedzie w lewo szybko)
  Inne kierunki: sprity 37, 38, 40, 42, 43, 44 (ukośne i wolniejsze warianty)

Mapowanie DC2 y-offset (obliczone z atlasu):
  #37  ySrc= 948  26×30   (skręt w lewo)
  #38  ySrc= 978  20×30   (jazda w dół łagodna)
  #39  ySrc=1008  25×31   (skręt w prawo)
  #40  ySrc=1039  30×29   (szybka jazda ukośna)
  #41  ySrc=1068  32×32   (duże przechylenie w lewo)
  #42  ySrc=1100  32×32   (duże przechylenie w prawo)
  #43  ySrc=1132  25×29   (siad/powolna jazda)
  #44  ySrc=1161  29×25   (inny kierunek)

--- Call track: render jednej klatki NPC (gdy aktywny) ---

entity_type3 (stan 34-39) wywołuje co klatkę:
  call 0x947(encja, stan)    → aktualizuje [encja+0x0E] = stan, wybiera sprite

Rysowanie (analogiczne do gracza, przez DC2 atlas):
  BitBlt(DC6,    0,   0,  W, H,  DC2,   0, ySrc, SRCCOPY)  [Case 2B: wyciągnij sprite z atlasu]
  BitBlt(screen, x,   y,  W, H,  DC6,   0,    0, SRCCOPY)  [Case C:  blit na ekran]
  gdzie W×H = wymiary sprite'a (np. 26×30 dla #37), x/y = pozycja na ekranie

--- Inicjalizacja ścieżki NPC (func_0x36A5 @ CS:0x36A5) ---

Wywoływana jednorazowo z 0x3CEB podczas startu gry.
Oblicza punkty trasy NPC wzdłuż obu stron ekranu (linia gondoli i krawędzie):
  [0xb6a] = DC handle atlasu używany do rysowania tła
  [0xb94] = bufor danych encji (0x1A00 bajtów = do 256 encji × 26 bajtów)
  [0xb82] = licznik aktywnych encji NPC (reset do 0, inkrementowany przy alloc)
Funkcja func_0x2b65 (CS:0x2b65) zeruje licznik: mov [0xb82], 0.

--- Pełny call track od game_loop ---

game_loop (CS:0x3F8A):
  → [co klatkę] call render_frame (CS:0x34FB)
    → call 0x3342 (main entity update loop)
      → iteruj listę encji [0xb7c]
        → dla każdej encji: call entity_update_dispatch (CS:0x2667)
          → switch [encja+0xc]:
            case 3: call entity_type3 (CS:0x2594)   ← NPC narciarz
              → maszyna stanów (patrz wyżej)
              → call 0x947(encja, stan) → zapisz stan animacji
            case 9: call entity_type9 (CS:0x251E)   ← yeti
      → rysowanie encji (via DC2/DC4 atlas → DC6 → screen)

=== WIN16 TLO I RUCH SPRITEOW ===

W Windows 3.1 GDI NIE ma żadnego automatycznego save-behind dla sprite'ów.
Stare pozycje sprite'ów są kasowane przez background rendering gry (terrain drawing,
FillRect na śnieg) wykonywanym NA POCZĄTKU każdej klatki — nie przez GDI.

DC6 dostaje świeże tło przez Case 2B (DC4→DC6): kopiuje wybrany wiersz atlasu
(= konkretny sprite) do DC6 z alpha=1 tylko na piksele sprite'a. Case C blit
(DC6→screen) zapisuje tylko alpha=1 piksele, reszta ekranu niezmieniona.

Brak ruchu gondoli (problem do zbadania):
  - Gondola (sprite #27: kabina; #64: słup masztu) porusza się pionowo (wyciąg).
  - W śladzie gry loop widzimy tylko DC4→DC6→screen (duże sprite'y, klatki skoczka).
  - Gondola i słup są małymi spriteami (DC2), mogą być renderowane w innej ścieżce
    albo poza limitem 600 wywołań trace'u.
  - Do zbadania: czy gondola używa Case B (SRCAND+SRCPAINT) albo SRCPAINT->DC6->screen.

=== ATLAS LAYOUT ===

Small sprites (1..26, 28..52, 64..86) -> DC2 (buf_sel=0x0130):
  Sprites stacked vertically: sprite N at y = sum(heights of sprites 1..N-1)

Large sprites (27, 53..63) -> DC4 (buf_sel=0x0260):
  Same vertical stacking.

During game loop, DC4 is read with varying ySrc to pick the right sprite frame.
